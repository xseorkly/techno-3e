Avant de commencer : votre mission

Les administrateurs d'Horizon n'ont pas tous un poste dédié ; on ignore si les contrôles d'identité couvrent tous les équipements. Une erreur sur le plan de contrôle pourrait affecter les comptes de tous les utilisateurs.

Ce que vous devez comprendre

RSAT permet d'utiliser des consoles et commandes d'administration depuis un poste Windows. Une forêt AD regroupe un ou plusieurs domaines ; un contrôleur de domaine (DC) héberge les services d'annuaire. Une GPO configure des paramètres mais son existence ne prouve pas son application. Une politique de mot de passe granulaire peut s'appliquer à certains utilisateurs.

Comment procéder concrètement

Ouvrir les preuves d'identité, puis identifier le rôle et la limite de chaque contrôle. Dans la VM seulement, exécuter le script de lecture, examiner le JSON, puis comparer aux observations PingCastle du laboratoire. Pour chaque anomalie, demander une seconde preuve. Ne pas traiter un score comme une vérité absolue.

Ce que vous devez remettre

Une ligne par contrôle : observation, preuve, impact, mesure et test. Exemple : deux usages privilégiés mêlés à la bureautique → risque sur le plan de contrôle → proposer un compte dédié et vérifier que l'accès de test autorisé fonctionne uniquement depuis le canal approuvé.

Objectifs d’ingénierie

Évaluer la qualité de preuve d’un annuaire : domaines/forêt, niveau fonctionnel, résilience des DC, politiques de mot de passe, comptes privilégiés, contrôle du plan d’administration, cycle de vie des identités et PKI. Une politique de domaine ne prouve pas sa mise en œuvre pour tous les utilisateurs.

Étape A — collecte PowerShell agrégée

  1. Sur le poste RSAT du domaine de test, ouvrir Windows PowerShell avec un compte habilité en lecture.
  2. Télécharger lab-collecte-ad.ps1 ; lire les commandes avant exécution. Le script ne crée pas de compte, ne change pas de stratégie et n’exporte aucun secret.
  3. Exécuter en remplaçant le domaine par le domaine fictif effectivement installé et en choisissant un dossier local protégé.
.\lab-collecte-ad.ps1 -LabDomain "horizon.test" -OutputDirectory "C:\AuditLab\AD"

Inspecter ad-summary.json et l’empreinte SHA-256. Si le module AD est absent, utiliser preuves-identite.csv. Vérifier le nombre de DC par rapport au plan de reprise ; le nombre d’objets ordinateurs n’est pas le nombre de postes actifs.

Étape B — audit PingCastle

PingCastle est un outil d’évaluation de la posture AD. Consulter le site de l’éditeur et les conditions de licence applicables ; télécharger uniquement une distribution officielle et vérifier son intégrité. En laboratoire, utiliser le mode Healthcheck proposé par la version installée, avec un compte de consultation autorisé. Les options et conditions peuvent varier : consulter l’aide de la version fournie. Ouvrir le rapport HTML local ; ne pas le publier ni le transférer à une IA externe.

Étape C — rendre les décisions testables

Analyser preuves-identite.csv. Produire une matrice avec écart, preuve, impact, mesure compensatoire, dépendance, test positif et négatif, plan de rollback. Exemples : vérifier LAPS sur un poste fictif sans afficher de mot de passe ; tester un changement LDAP dans une OU pilote après inventaire des clients hérités ; documenter le retrait d’un droit excessif avec une identité de test.

Ne pas traiter le score d’un outil comme une certification.

Avant de commencer : votre mission

Le scanner remonte une alerte concernant un serveur. La direction vous demande s'il faut interrompre le service immédiatement. Le rapport mentionne un produit mais le correctif réellement installé n'est pas encore connu.

Ce que vous devez comprendre

Greenbone utilise des tests de vulnérabilité (VT) alimentés par des feeds, c'est-à-dire des catalogues actualisés de tests et de connaissances. Une détection distante peut reposer sur un indice ; une détection authentifiée peut accéder à des informations de version plus fiables. Le niveau de qualité de détection est un indicateur, pas une preuve absolue.

Comment procéder concrètement

Dans la console de laboratoire préparée, observer l'état des feeds et le rapport de démonstration ; repérer les colonnes de cible, résultat, sévérité et qualité de détection. Relever un résultat, chercher sa référence officielle et comparer la version. Si le rapport réel de laboratoire manque, ouvrir les constats fictifs. Lancer uniquement les tâches de laboratoire prévalidées par le formateur.

Ce que vous devez remettre

Un tableau de deux constats minimum : source, date, produit/version, CVE si disponible, preuve, incertitude, priorité et validation. Exemple : version non corroborée → investigation, pas « vulnérabilité confirmée ».

Différencier découverte, détection par version, contrôle authentifié et validation éditeur. Une absence de résultat n’est pas une preuve d’absence de vulnérabilité.

Pas à pas sur laboratoire

  1. Consulter le guide des conteneurs officiels. Sur Linux dédié, installer Docker/Compose selon la politique de l’établissement. Utiliser le fichier Compose fourni par l’éditeur et examiner les volumes, ports, comptes et images avant démarrage.

  3. Le formateur crée une cible de test unique, isolée, avec autorisation et fenêtre définies. Préparer une tâche non destructive validée par le formateur ; pas de recherche générale sur les sous-réseaux.
  4. Comparer un rapport préétabli de détection distante avec un rapport authentifié obtenu en laboratoire. Aucun identifiant réel ni secret dans les rapports pédagogiques.
  5. Dans le rapport, relever actif fictif, horodatage, produit, version, méthode, qualité de détection, CVE si disponible, score et bulletin éditeur. Exporter le format disponible (CSV/XML selon la version).
  6. Effectuer la revue des constats avec le fichier constats-horizon.csv. Documenter faux positif, version incertaine, correctif rétroporté, actif hors périmètre et information manquante.

Avant de commencer : votre mission

Le responsable informatique doit traiter plusieurs alertes chaque semaine et souhaite éviter les recherches manuelles répétitives. Il doit néanmoins vérifier que le signal public s'applique à son SI.

Ce que vous devez comprendre

API = interface de programmation permettant d'interroger un service via une requête structurée. JSON = format textuel de données. Le CVE est un identifiant ; la fiche NVD fournit des métadonnées et références ; l'avis éditeur précise souvent les versions et correctifs. Une réponse vide ou une erreur API n'est pas une preuve d'absence de faille.

Comment procéder concrètement

Télécharger le script, le lire puis l'exécuter uniquement avec l'identifiant public fourni. Ouvrir le JSON et identifier les champs id, status, modified, references et retrievedUtc. Choisir une référence éditeur vérifiable. Reporter les informations manquantes si le service ne répond pas.

Ce que vous devez remettre

Une fiche de veille : identifiant, source, date de consultation, produit, état de vérification, avis éditeur et limites. Ne pas envoyer de nom d'actif, IP interne ou version issue du SI à l'API.

Les référentiels publics fournissent des signaux différents. CVE identifie ; NVD enrichit ; CVSS décrit la sévérité ; EPSS estime une probabilité d’exploitation à 30 jours à l’échelle mondiale ; KEV signale des vulnérabilités exploitées connues. Aucun ne démontre à lui seul l’applicabilité à un actif.

Récupération d’une fiche publique

Télécharger lab-api-cve.ps1. Le script effectue une requête HTTPS unique à l’API officielle NVD pour un identifiant public ; il n’envoie ni IP interne, ni version issue du SI, ni nom de machine.

.\lab-api-cve.ps1 -CveId CVE-2021-44228

Conserver le statut, la date de modification, l’horodatage de collecte et les liens vers l’éditeur. Pour l’exercice, rechercher la fiche publique sans reproduire la vulnérabilité ni tester son exploitation. Si NVD est indisponible ou limite les requêtes, consulter la fiche CVE et les avis éditeurs manuellement.

Avant de commencer : votre mission

La direction veut savoir quand un test de restauration échoue, avant de découvrir au moment d'une crise que la sauvegarde est inutilisable. Vous devez créer une règle simple et démontrer qu'elle détecte l'événement voulu, sans alerter sur les succès.

Ce que vous devez comprendre

Un agent collecte des événements ; le manager décode le message et applique des règles ; l'indexeur rend les événements consultables. Un décodeur transforme les données en champs ; une règle compare ces champs à des conditions ; un faux positif est une alerte injustifiée, un faux négatif une absence d'alerte attendue. Un niveau de règle n'est pas la gravité métier.

Comment procéder concrètement

Ouvrir lab-wazuh.json dans un éditeur et repérer les deux lignes. Ouvrir la règle XML et associer chaque condition à un champ JSON. Sur le manager de test, vérifier l'identifiant de règle, intégrer le fragment selon la documentation, lancer logtest, puis coller une ligne à la fois. Noter le résultat de décodage et la règle correspondante. Si Wazuh n'est pas disponible, simuler la comparaison à la main.

Ce que vous devez remettre

Deux cas de test : résultat=failed → règle 100120 attendue ; résultat=success → règle 100120 non attendue. Capturer ou noter les résultats réels, la version et les écarts. Calculer ensuite le volume théorique pour 1 200 postes ; ne pas confondre volume brut et disque nécessaire.

Architecture et dimensionnement

Agents / sources
Manager : décodage et règles
Indexer : rétention
Dashboard / traitement des alertes

Pour 1 200 agents, dimensionner sur des mesures d’EPS, la taille moyenne des événements, le taux d’indexation, la compression, la rétention et les réplicas. Hypothèse : 1 200 × 0,5 EPS = 600 événements/s. À 1 Ko/événement : 51,84 Go/jour bruts (unités décimales), soit 1,555 To pour 30 jours avant indexation, réplication et marge. Mesurer en pilote, ne pas utiliser cette estimation comme capacité garantie.

Installation préparatoire

  1. Sur un serveur Linux isolé, suivre le Quickstart officiel, ou le guide distribué pour une architecture plus importante. Vérifier versions compatibles, certificats, stockage et accès.
  2. Depuis le dashboard, utiliser l’assistant de déploiement d’un agent sur le client Windows de test, conformément au guide Windows. Vérifier agent actif, heure et réception d’un événement bénin.
  3. Définir une collecte proportionnée : journaux de sécurité autorisés, état des agents, alertes et rétention. Aucun contenu de messagerie ou d’élèves dans le lab.

Créer et tester un contrôle de détection

Les deux événements lab-wazuh.json décrivent un test de restauration échoué puis réussi. La règle lab-wazuh-regle.xml détecte uniquement l’échec.

  1. Sur le manager de laboratoire, sauvegarder les règles locales, vérifier que l’identifiant 100120 est libre et intégrer le fragment XML au fichier local de règles conformément à la version installée. Ne pas écraser les autres règles.

sudo /var/ossec/bin/wazuh-logtest

Avant de commencer : votre mission

Un flux entre le réseau des élèves et l'administration semble autorisé sans justification. Vous devez déterminer ce que la capture réseau et la matrice de flux permettent réellement de démontrer.

Ce que vous devez comprendre

Un paquet transporte des informations de communication. DNS traduit notamment un nom en adresse ; TCP/UDP sont des protocoles de transport. Une capture PCAPNG contient des paquets observés sur une interface. Un filtre d'affichage sélectionne les paquets visibles sans changer la capture. Une capture en un point ne prouve pas qu'un pare-feu applique correctement toute sa politique.

Comment procéder concrètement

Comparer les CSV, puis créer la capture synthétique depuis le fichier hex fourni. Ouvrir le PCAPNG, afficher le filtre dns, sélectionner les deux requêtes et développer la couche DNS. Relever nom demandé et type A (IPv4) ou AAAA (IPv6). Les autres filtres ne sont pas censés produire des résultats sur cette capture DNS seule.

Ce que vous devez remettre

Un tableau des deux requêtes et une conclusion séparée sur le flux SMB fictif. La capture DNS ne démontre ni l'acceptation ni le refus du flux SMB ; pour cela il faut un test dédié en laboratoire et les journaux du pare-feu.

Ne pas capturer les flux réels des élèves ou personnels. Le TP utilise des métadonnées fictives et une capture locale facultative entre deux VM de test, uniquement avec un trafic de test non sensible.

Analyse des métadonnées (sans installation)

  1. Ouvrir lab-flux-observes.csv et matrice-flux.csv.
  2. Réconcilier zone source, zone destination, service, action et ticket de changement. Repérer l’écart entre besoin métier et règle effective.
  3. Construire un test positif et négatif par flux : service autorisé fonctionnel ; flux interdit refusé, preuve dans les journaux du pare-feu.

Analyse Wireshark sur une capture locale de laboratoire

Installer depuis le site officiel. Télécharger lab-dns.hex, contenant deux requêtes DNS fictives pour des noms réservés en .test. Dans un terminal où text2pcap (fourni avec Wireshark) est accessible, convertir ce fichier en PCAPNG : 

text2pcap -u 53000,53 lab-dns.hex lab-dns.pcapng
Ouvrir lab-dns.pcapng dans Wireshark. Ce fichier synthétique ne contient que deux requêtes DNS, aucune réponse et aucun trafic TLS ou TCP ; les autres filtres sont à appliquer à une capture de test complémentaire produite par le formateur. Les filtres d’affichage n’altèrent pas le fichier source. Dans Statistics → Conversations, examiner les communications agrégées. Appliquer les filtres suivants successivement.

dns
tls.handshake.type == 1
tcp.analysis.retransmission
icmp || icmpv6

Exporter uniquement des métadonnées nécessaires au test. En ligne de commande, analyser un fichier PCAP de test sans capture active :

tshark -r lab-dns.pcapng -Y "dns" -T fields -e frame.time_epoch -e ip.src -e ip.dst -e dns.qry.name

Le fichier PCAPNG se génère à partir de lab-dns.hex ; on attend deux requêtes, horizon.test (A) et app.horizon.test (AAAA). Les adresses de l’en-tête synthétique sont créées par text2pcap et ne représentent aucun réseau réel. Les champs IPv4 peuvent être vides sur IPv6. Une retransmission n’est pas automatiquement un incident de sécurité. Un refus ne se démontre pas uniquement par l’absence de paquet dans une capture ; croiser source, destination, journal et politique.

Invités → administration refusé correspond à la politique cible. Les flux autorisés nécessitent encore un test positif et un propriétaire ; ne pas appliquer un changement sans validation ni rollback.
