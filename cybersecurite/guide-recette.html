01 — Pourquoi tester avant de déployer ?

AVANT L'ATELIER · PARTAGE D'EXPÉRIENCE

Et dans votre établissement, comment faites-vous ?

En tant que responsable informatique d'un établissement français à l'étranger, prenez quelques minutes pour présenter vos pratiques existantes et leurs limites. Échangez avec un collègue avant d'étudier la démarche proposée. Si ces questions ont déjà été abordées, reprenez vos notes. N'indiquez aucune donnée sensible.

Après l'atelier : ce que je conserve, adapte et améliore

Les réponses restent sur cette page, sans sauvegarde automatique. Exportez-les avant de quitter.

Situation professionnelle

Le lycée Horizon dispose de 1 200 postes. La direction vous demande de proposer une solution d'audit automatisée et une surveillance de sécurité. Vous avez téléchargé des scripts, choisi plusieurs logiciels et préparé un plan de sécurisation. Mais comment prouver qu'ils fonctionnent, qu'ils produisent des informations fiables et qu'ils ne perturbent pas le SI ?

Une recette technique consiste à définir ce que l'on attend d'un système, à réaliser des essais reproductibles, puis à comparer les résultats observés aux résultats attendus. Elle n'est ni un simple contrôle de démarrage, ni un certificat de sécurité.

Votre mission : tenir un procès-verbal de recette ; pour chaque essai, préciser le résultat attendu, le résultat observé, le statut, la preuve et l'action à mener si nécessaire.

Durée indicative : introduction 10 minutes ; les tests s'intègrent aux ateliers existants. La préparation des VM et la recette complète sont à réaliser avant la session par le formateur ou en prolongement autonome. Elles ne s'ajoutent pas aux 12 heures prévues.

02 — Préparer un environnement de test sûr

Pourquoi une VM plutôt que le réseau de l'établissement ?

Une machine virtuelle est un ordinateur logiciel hébergé par un hyperviseur. Elle permet d'expérimenter sans modifier les serveurs et postes réels. Elle ne constitue pas à elle seule une isolation réseau : son adaptateur peut être connecté au réseau de l'établissement si le mode pont est utilisé. Un scanner ou une mauvaise configuration pourrait alors affecter des équipements réels.

  1. Utiliser l'hyperviseur validé par le formateur (Proxmox, Hyper-V, VirtualBox ou autre). Créer un réseau privé de laboratoire, sans pont vers la production et sans route vers le SI réel.
  2. Préparer Windows Server/AD DS, un client Windows avec RSAT, et des VM Linux dédiées aux outils Greenbone et Wazuh si disponibles. Pour le traitement des fichiers, un poste d'analyse suffit.
  3. Installer les logiciels à partir des sources officielles, avec accès Internet contrôlé uniquement lorsque nécessaire. Vérifier les versions, les ressources et les conditions de licence. Déconnecter les interfaces non nécessaires avant les manipulations.
  4. Utiliser exclusivement des comptes fictifs, un domaine de test et les fichiers du lycée Horizon. Vérifier la topologie réseau avec le formateur. Si l'isolation n'est pas démontrée, ne pas lancer de scan.
  5. Créer un snapshot lorsque l'état de référence est sain. Noter le nom de la VM, sa version, sa date et la configuration. Le snapshot facilite le retour arrière dans le laboratoire ; il ne remplace pas une sauvegarde indépendante.
  6. Créer un dossier de preuves local et protégé. Ne pas publier de rapports réels sur GitHub, dans un espace public ou dans une IA externe.
À remettre : une fiche indiquant les composants, les versions, le réseau isolé, les ressources, les snapshots et les solutions de repli. Consulter les prérequis détaillés.

03 — Lancer les tests automatisés avec GitHub Actions

Pourquoi automatiser la recette ?

Un test réalisé sur votre ordinateur peut dépendre de logiciels déjà installés ou d'un environnement particulier. GitHub Actions exécute un workflow, c'est-à-dire une liste de tâches décrites dans un fichier YAML, sur des machines hébergées appelées runners. Cela rend la recette répétable et permet de détecter une régression lorsqu'un fichier change. Un runner Windows standard n'est pas un domaine Active Directory ; il ne remplace pas le laboratoire d'identité.

Pas à pas

  1. Ouvrir le workflow Recette cybersécurité Horizon. La lecture des résultats publics ne nécessite pas les mêmes droits que le déclenchement d'une exécution.
  2. Sur le dépôt du formateur, seul un compte autorisé en écriture peut cliquer sur Run workflow, sélectionner main, puis confirmer. Les stagiaires sans droits utilisent une exécution déjà disponible ou un dépôt de laboratoire personnel autorisé contenant uniquement les fichiers fictifs. Si le bouton n'apparaît pas, demander au formateur ; ne pas demander de droits sur le dépôt de production.
  3. Dans la liste des exécutions, ouvrir celle qui correspond au bon commit. Vérifier son état : queued = en attente, in progress = en cours, success = réussite, failure = échec. Un workflow non exécuté n'a aucun résultat.
  4. Ouvrir le job Linux puis le job Windows. Développer chaque étape et lire les logs. Un job arrêté prématurément ne valide pas les étapes suivantes.
  5. Si les fichiers de résultat ont été générés, retrouver les artifacts recette-linux et recette-windows, puis télécharger les preuves. Les artifacts ont une durée de conservation de sept jours dans le workflow actuel.
  6. Inscrire le lien de l'exécution, le commit, la date et la conclusion de chaque étape dans le PV. Si un téléchargement ou une API est indisponible, noter « bloqué » et la cause, pas « réussi ».
JobCe qui est prévuCe qui n'est pas prouvé
LinuxExécution Python, installation TShark, génération et lecture du PCAPNG DNS.Sécurité du réseau de l'établissement, fonctionnement du scanner Greenbone.
WindowsAnalyse syntaxique des scripts PowerShell ; requête NVD publique.Collecte réelle AD, application des GPO, fonctionnement de PingCastle.
ArtifactsRapport Python, DNS, capture et JSON NVD si générés.Conformité de tous les systèmes ou absence de vulnérabilité.
État actuel : le workflow est publié ; aucune exécution sur VM n'a été confirmée par le connecteur. Les exercices sur AD, PingCastle, Wazuh et Greenbone se font dans des VM dédiées préparées par le formateur. Rapport des tests effectivement réalisés.

04 — Vérifier l'intégrité de la collecte et des scripts

A. Pipeline Python

Pourquoi ? Si un inventaire contient un doublon, le nombre d'équipements et les pourcentages de couverture peuvent être faux. Une erreur de jointure peut également attribuer un problème à la mauvaise machine. Nous voulons que le programme échoue explicitement plutôt que de présenter un résultat trompeur à la direction.

  1. Télécharger lab-actifs.csv, lab-controles.csv et lab-audit.py dans un même dossier. Ouvrir les CSV et repérer asset_id, edr, patch_evidence, status et evidence_id.
  2. Ouvrir un terminal dans le dossier. Vérifier la présence de Python 3 (python --version, python3 --version ou py -3 --version selon l'installation).
  3. Exécuter le programme avec le jeu initial. Le résultat doit être du JSON.
python lab-audit.py

Résultat attendu : 6 actifs ; 4 avec EDR actif ; 4 avec preuve de correctifs fraîche ; 66,67 % pour chacun ; 2 pass, 2 fail et 2 unknown. Les contrôles E02 et E04 sont des échecs fictifs ; E01 et E03 sont des preuves manquantes.

  1. Dans une copie du dossier, ajouter un doublon de LAB-01 dans le CSV d'actifs. Relancer. Le programme doit s'arrêter en indiquant le doublon.
  2. Revenir à la version initiale. Dans la copie du fichier des contrôles, remplacer un asset_id par LAB-99. Relancer. Le programme doit refuser cette référence.
  3. Restaurer les fichiers fictifs originaux et enregistrer le rapport nominal. Conserver les deux messages d'erreur comme preuves de tests négatifs.

B. PowerShell : syntaxe avant exécution

Un script peut contenir une erreur de syntaxe empêchant son lancement. Le parseur PowerShell permet de contrôler sa structure sans exécuter ses commandes. Ce contrôle ne garantit pas que les modules, droits, serveurs ou résultats métier sont corrects.

Télécharger les scripts du laboratoire, ouvrir PowerShell dans le dossier, puis tester le fichier sans l'exécuter.

$tokens = $null
$errors = $null
[void][System.Management.Automation.Language.Parser]::ParseFile((Join-Path (Get-Location) 'lab-collecte-ad.ps1'), [ref]$tokens, [ref]$errors)
$errors | Format-List
$errors.Count

Attendu : 0 erreur. Refaire le contrôle pour lab-api-cve.ps1 et collecte.ps1. Si la syntaxe est valide, l'exécution réelle de la collecte reste à valider dans le domaine de test.

Preuves : rapport Python, deux refus explicites et résultat de parsing des trois scripts. TP complet Python + IA.

05 — Vérifier la collecte Active Directory et PingCastle

Pourquoi ? Active Directory centralise les identités et les droits. Si la collecte utilise un mauvais domaine ou si l'on confond les objets enregistrés avec les postes actifs, l'analyse peut être gravement inexacte. Une politique de domaine peut aussi différer de la politique réellement appliquée à un utilisateur. PingCastle fournit des signaux de posture, pas une certification.

  1. Sur le client Windows de laboratoire préparé, vérifier le module ActiveDirectory (RSAT) et le domaine de test avec le formateur. Utiliser un compte habilité en lecture. Ne pas modifier le domaine de production.
  2. Télécharger et relire lab-collecte-ad.ps1. Vérifier que le domaine et le dossier de sortie correspondent au laboratoire.
  3. Exécuter la commande ci-dessous en adaptant uniquement le nom du domaine de test.
.\lab-collecte-ad.ps1 -LabDomain "horizon.test" -OutputDirectory "C:\AuditLab\AD"
  1. Ouvrir ad-summary.json et relever domainControllerCount, computerObjectCount, enabledComputerObjects et fineGrainedPolicyCount. Comparer les chiffres à la console AD de laboratoire.
  2. Calculer l'empreinte du rapport avec Get-FileHash -Algorithm SHA256 C:\AuditLab\AD\ad-summary.json et comparer au fichier d'empreinte généré. L'égalité confirme que le contenu n'a pas changé entre les deux calculs, pas que les observations sont exactes.
  3. Dans le laboratoire, suivre le mode Healthcheck de la version de PingCastle fournie par le formateur, après vérification de la licence. Ouvrir le rapport local. Sélectionner deux observations et rechercher les preuves complémentaires dans les consoles de test.
  4. Si RSAT, AD ou PingCastle ne sont pas disponibles, ouvrir preuves-identite.csv ; préciser que vous analysez des données fictives et non un audit AD réel.
Attendu : collecte JSON cohérente, empreinte concordante, deux constats interprétés, limites et propositions de contrôle. Approfondissement AD / PingCastle.

06 — Vérifier les sources de vulnérabilités et Greenbone

A. Interroger une API officielle

Pourquoi ? Une IA ou un rapport peut citer une référence incorrecte. Une API publique permet de récupérer des données structurées et datées. La présence d'un CVE dans NVD ne démontre pas qu'il concerne un équipement de l'établissement.

  1. Avec un accès Internet autorisé, télécharger lab-api-cve.ps1 ; lire le script et vérifier qu'il n'envoie qu'un identifiant CVE public.
  2. Exécuter la commande. Si l'API est indisponible, noter la date et l'erreur.
.\lab-api-cve.ps1 -CveId CVE-2021-44228

Attendu : id exact, statut, dates, références éditeurs et horodatage de collecte. Tester également une valeur invalide, par exemple TEST : le script doit la refuser avant la requête. Ne pas tester l'exploitation de la vulnérabilité.

B. Contrôler la fiabilité d'un rapport de scanner

Greenbone rassemble des tests de vulnérabilité issus de catalogues (feeds). Un feed ancien ou une cible non accessible peut donner un résultat incomplet. Une version détectée peut aussi être approximative. Un scan sur un SI réel peut générer de la charge ou perturber un service.

  1. Dans la console de laboratoire préinstallée, vérifier la version et la fraîcheur des feeds, puis noter ces informations.
  2. Ouvrir le rapport de démonstration fourni par le formateur. Si une tâche doit être lancée, le formateur valide une seule cible de laboratoire isolée et les paramètres non destructifs. Ne pas lancer de découverte générale.
  3. Choisir deux résultats. Pour chacun, relever le produit, la version, la méthode de détection, la référence et les limites. Chercher un avis éditeur et une preuve locale de la version exacte.
  4. Comparer à constats-horizon.csv. Classer confirmé, hypothèse ou inconnu. Indiquer pourquoi et ce qu'il faut vérifier.
  5. En l'absence de scanner installé, utiliser les rapports fictifs. Ne pas présenter ces fichiers comme des résultats générés par Greenbone.
À remettre : une fiche CVE publique et deux constats de scanner documentés. TP Greenbone · TP API CVE.

07 — Tester une règle de détection avec Wazuh

Situation : le lycée pense que les sauvegardes fonctionnent. Un test de restauration échoue, mais personne ne reçoit d'alerte. Comment démontrer que l'équipe sera avertie au prochain échec sans générer une alerte pour chaque succès ?

Le SIEM collecte et interprète des événements. Si la règle est trop large, elle génère du bruit et les équipes peuvent manquer un incident important ; si elle est trop restrictive, elle laisse passer un signal utile. Il faut un test positif et un test négatif.

  1. Télécharger lab-wazuh.json et lab-wazuh-regle.xml. Dans le JSON, repérer horizon.event et horizon.result : les deux lignes représentent un test de restauration échoué et réussi.
  2. Dans le XML, repérer l'identifiant 100120, le décodeur JSON et les deux conditions. Les conditions doivent correspondre à un événement backup_restore et à un résultat failed.
  3. Sur le manager Wazuh de laboratoire uniquement, suivre les instructions de la version installée pour ajouter le fragment à la configuration de règles locales. Le formateur vérifie l'identifiant libre et conserve la configuration précédente.
  4. Exécuter le test de règle, sans utiliser un SIEM de production.
sudo /var/ossec/bin/wazuh-logtest
  1. Coller la première ligne JSON complète, lire les phases de décodage et la règle finale. Résultat attendu : la règle 100120 correspond.
  2. Coller la deuxième ligne. Résultat attendu : la règle 100120 ne correspond pas. D'autres règles peuvent correspondre selon la configuration.
  3. Quitter l'outil, noter la version de Wazuh et conserver les résultats. En cas d'échec, vérifier les noms des champs décodés, l'identifiant et la syntaxe du fragment avec le formateur.

Si Wazuh n'est pas disponible, comparer manuellement les deux JSON aux conditions XML. Cela valide seulement la logique théorique, pas le moteur Wazuh.

À remettre : deux résultats distincts et une décision : conforme, non conforme, bloqué ou simulé. TP et dimensionnement SIEM.

08 — Vérifier la génération et l'analyse d'une capture réseau

Pourquoi ? Une capture réseau permet d'observer des échanges réels, mais peut contenir des identifiants, des adresses et des données personnelles. Pour apprendre à lire les paquets sans exposer des personnes, nous fabriquons une petite capture synthétique dont le contenu est connu à l'avance.

  1. Installer Wireshark depuis le site officiel sur le poste de laboratoire ou utiliser les outils en ligne de commande installés par le formateur. Vérifier que text2pcap et tshark sont disponibles dans le terminal.
  2. Télécharger lab-dns.hex dans le dossier de travail. Le fichier contient deux requêtes DNS synthétiques, aucune réponse et aucune donnée réelle.
  3. Convertir le contenu hexadécimal en capture PCAPNG. Cette opération fabrique des paquets dans un fichier, elle n'envoie pas de requête sur le réseau.
text2pcap -u 53000,53 lab-dns.hex lab-dns.pcapng
  1. Dans Wireshark, choisir File → Open, ouvrir lab-dns.pcapng. Saisir dns dans la barre de filtre d'affichage puis valider. Observer les deux paquets.
  2. Cliquer sur un paquet et développer Domain Name System → Queries. Relever le nom et le type de requête. Vérifier avec TShark.
tshark -r lab-dns.pcapng -Y "dns" -T fields -e dns.qry.name -e dns.qry.type

Résultat attendu : horizon.test, type 1 (A, IPv4), puis app.horizon.test, type 28 (AAAA, IPv6). Aucun paquet TLS ou TCP n'est prévu dans cette capture.

À remettre : une capture ou sortie TShark annotée et une phrase expliquant que cette vérification ne démontre pas le cloisonnement du SI. TP analyse des flux.

09 — Vérifier les interfaces et exports du site

Pourquoi ? Un formulaire qui semble fonctionner peut perdre les données lors de l'export. Le responsable informatique doit pouvoir ouvrir les fichiers et vérifier leur contenu avant de les utiliser comme preuve.

  1. Ouvrir la fiche pays, sélectionner un pays et renseigner trois résultats entièrement fictifs, avec accents, point-virgule et guillemets. Générer le prompt et vérifier qu'il reprend les paramètres choisis.
  2. Exporter le CSV. L'ouvrir dans un tableur en utilisant UTF-8 et le séparateur point-virgule si nécessaire. Comparer le nombre de lignes et le contenu aux champs saisis.
  3. Réaliser le même contrôle sur la checklist RGPD et le carnet de formation. Exporter avant de fermer la page : les champs ne sont pas sauvegardés automatiquement.
  4. Vérifier sur un écran étroit que les liens, boutons, champs et tableaux restent accessibles. Noter les éventuelles anomalies.

Ne jamais utiliser de noms d'élèves, configurations réelles ou secrets. Si l'export échoue, conserver une note locale fictive et signaler le problème.

10 — Rédiger le procès-verbal de recette

Une conclusion professionnelle ne se résume pas à « tout fonctionne ». Elle indique ce qui a été exécuté, dans quel environnement, ce qui a échoué et quelles limites demeurent. Un test simulé n'est pas un test logiciel exécuté ; un test bloqué ne valide rien. Utiliser les résultats pour décider du passage à l'étape suivante.
